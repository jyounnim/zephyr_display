# Lab 03: OLED SSD1306 (I2C 모드, 주소 자동 감지)

## 1. 개요

보드는 **Synaptics SR110** (`sr100_rdk/sr100/m55`), 프레임워크는 **Zephyr RTOS**를 사용합니다.

0.96인치 SSD1306 128x64 모노크롬 OLED를 **I2C 모드**로 구동합니다. SSD1306 I2C 모듈은 실장된 저항(SA0 스트랩)에 따라 **0x3C 또는 0x3D** 두 주소 중 하나로 동작하는데, 이 랩은 01번 랩(I2C bus scanner)과 같은 방식으로 부팅 시 두 주소를 직접 스캔해서 실제로 응답하는 쪽을 자동으로 골라 씁니다.

이 랩은 Zephyr의 Display/CFB 서브시스템이나 in-tree `solomon,ssd1306` 드라이버를 쓰지 않고, **02번 랩(PCF8574 LCD)과 동일하게 raw I2C**로 SSD1306을 직접 제어합니다 — 그 이유는 3절에서 설명합니다.

## 2. 왜 raw I2C인가 (Zephyr 표준 드라이버를 안 쓰는 이유)

Zephyr의 `solomon,ssd1306` 드라이버는 devicetree 노드에 `reg = <0x3C>;`처럼 **주소를 빌드 타임에 고정**해서 씁니다. 그런데 이 랩의 목적 자체가 "부팅 시 실제 연결된 주소를 스캔해서 자동으로 고르는 것"이라, 애초에 정적 devicetree 바인딩과는 맞지 않습니다. 그래서 05번 랩(SPI 모드 SSD1306, 고정 주소 불필요)과 달리, 이 랩은 devicetree에 SSD1306 노드를 아예 선언하지 않고 `main.c`에서 직접 I2C 명령/데이터를 씁니다.

## 3. SSD1306 I2C 프로토콜 요약

SSD1306과의 모든 I2C 트랜잭션은 **컨트롤 바이트**로 시작합니다:

| 컨트롤 바이트 | 의미 |
|---|---|
| `0x00` | 뒤따르는 바이트(들)는 **명령(command)** |
| `0x40` | 뒤따르는 바이트(들)는 **픽셀 데이터(GDDRAM)** |

명령은 한 번에 하나씩(컨트롤 바이트+명령 바이트 2바이트), 프레임버퍼(1024바이트) 전체는 컨트롤 바이트(`0x40`)를 맨 앞에 붙인 **1025바이트를 하나의 `i2c_write()` 트랜잭션**으로 보냅니다.

> ✅ **실기로 확인된 이슈 (2026-09-02) — 화면에 노이즈 형태로 표시됨**: 최초 구현은 프레임버퍼를 복사하는 비용을 아끼려고 `i2c_transfer()`로 컨트롤 바이트(메시지1)와 프레임버퍼(메시지2, `I2C_MSG_STOP`만 지정)를 "STOP 없이 이어붙이는" 방식을 썼습니다. 실기에서는 코드가 에러 없이 완료됐는데도 화면에 텍스트 대신 **노이즈 형태의 점들**이 나오는 문제가 재현됐습니다.
>
> 가장 유력한 원인은 **이 SR110 designware I2C 드라이버가 `i2c_transfer()`의 "메시지 사이 STOP 없이 이어서 전송" 시맨틱을 기대와 다르게 구현하고 있어서**, 두 메시지 사이에 원치 않는 STOP/새 트랜잭션이 끼어들었을 가능성입니다. 그러면 SSD1306 입장에서는 컨트롤 바이트(`0x40`) 하나만 있는 첫 트랜잭션과, **프레임버퍼의 첫 바이트가 새 컨트롤 바이트로 오인식되는** 두 번째 트랜잭션으로 쪼개져 버립니다 — 그 이후 모든 바이트가 한 칸씩 밀려서 해석되고, 어느 바이트가 명령/데이터로 읽히는지가 픽셀 값에 따라 사실상 랜덤해지므로, 딱 "노이즈"처럼 보이는 증상과 정확히 들어맞습니다.
>
> **조치**: 명령 전송에서 이미 안정적으로 동작하던 것과 동일하게, 컨트롤 바이트와 프레임버퍼를 **하나의 연속된 버퍼로 합쳐서 단일 `i2c_write()`**로 보내도록 변경했습니다. 정적 버퍼(1025바이트)를 하나 더 쓰는 대신, 이 드라이버의 멀티 메시지 처리 방식에 대한 가정 자체를 없앴습니다. 이 시리즈에서 `i2c_transfer()`(복수 메시지 API)를 시도했다가, SR110 플랫폼에서는 안전하지 않다고 판단해 되돌린 사례입니다 — 다른 랩에서 유사한 멀티 메시지 전송이 필요하면 이 경험을 참고하십시오.

## 4. 배선

| 신호 | 역할 | SR110 연결 |
|---|---|---|
| VCC | 전원 | 3.3V (아래 5절 전원 주의 참고) |
| GND | 그라운드 | GND |
| SDA | 데이터 | I2C0 SDA (핀 그룹 `i2c0_ms_sda`) |
| SCL | 클럭 | I2C0 SCL (핀 그룹 `i2c0_ms_scl`) |
| RST (모듈에 이 핀이 **있는 경우에만**, 아래 경고 참고) | 하드웨어 리셋 | gpioa 4 (SoC GPIO4, **J25 5번 핀**) — **아직 실기 미검증** |

알리익스프레스 등에서 흔히 파는 저가 SSD1306 모듈은 대부분 **VCC/GND/SDA/SCL 4핀뿐**이고 RST 핀 자체가 없습니다 — 이 경우 위 RST 행은 무시하면 됩니다. 01/02번 랩과 동일한 I2C0 버스를 그대로 재사용합니다.

> 🛑 **실기로 확인된 위험 — RST 핀 재사용 시도가 보드 전체 락업을 유발함 (2026-09-02)**: RST 핀이 나와 있는 모듈에서는 부팅 직후 점 노이즈가 뜨고 RST를 Low→High로 펄스해야 정상화되는 증상 자체는 실기로 확인됐습니다 (SSD1306 컨트롤러의 흔한 특성입니다). 문제는 그 RST 핀을 SR110의 **어느 GPIO에 연결할지**였습니다 — 처음에 "회로도상 SD0_CLK(GPIO26)는 이 프로젝트에서 SD카드를 안 쓰니 안전하다"고 판단해서 그 핀을 코드에서 자동으로 토글하게 만들었는데, **실기에서는 이 핀을 건드리자마자 부팅 배너조차 안 뜨는 완전한 락업**이 발생했습니다.
>
> **원인 재조사**: Zephyr SDK의 `sr100_pinctrl.dtsi`를 직접 열어보니, GPIO26이 속한 핀 그룹에는 `sd0_clk`뿐 아니라 `dm0_clk_a`(디버그 모듈 관련 신호)까지 alternate function으로 걸려 있었습니다. 회로도 넷 이름(SD0_CLK)만 보고 "SD카드 안 쓰니 안전"이라고 판단한 게 문제였을 수 있습니다 — pinctrl 파일까지 확인하지 않으면 그 핀이 정말 순수 GPIO 용도인지 알 수 없습니다.
>
> **현재 선택 (GPIO4, 아직 미검증)**: pinctrl 파일을 확인해서, JTAG/디버그모듈/SD 계열과 전혀 안 겹치는 핀(GPIO4 — 그룹 내 다른 기능은 `ciu_vsync_a`(미사용 카메라 VSYNC), `uart0_cts`(미사용 UART 흐름제어)뿐)으로 다시 골랐습니다. 다만 이 SoC의 devicetree 구조상 "이 핀을 GPIO로 강제한다"는 오버레이 설정 자체가 불가능해서(`i2c0`/`spi0`처럼 자기 `pinctrl-0`을 갖는 페리페럴과 달리, 맨 GPIO는 그런 자리가 없음), 결국 **SoC 리셋 시 mux 기본값이 GPIO라는 가정에 의존**하는 건 여전합니다. 즉 GPIO4도 "이번엔 더 신중하게 골랐다"뿐이지 **완전히 검증된 건 아닙니다.**
>
> **꼭 지켜주세요 — 안전한 확인 순서**:
> 1. 코드는 이미 `OLED_USE_HW_RESET=1`, `OLED_RST_PIN=4`로 설정되어 있습니다.
> 2. **OLED를 배선하기 전에 먼저 이 상태로 빌드/플래시**해서, GPIO4를 아무것도 안 연결한 채로 토글했을 때 **보드가 정상 부팅하고 시리얼 배너가 뜨는지부터** 확인하십시오.
> 3. 정상 부팅이 확인되면 그때 RST 핀을 J25 5번 핀에 배선하고 재확인하십시오.
> 4. 만약 이번에도 부팅 자체가 안 되면, 코드 상단의 `OLED_USE_HW_RESET`을 `0`으로 되돌리고 다른 핀을 시도하기 전에 알려주십시오 — `sr100_pinctrl.dtsi`를 같이 더 확인해보겠습니다.

## 5. 전원 주의 (01번 랩 문서 참고)

> ✅ **이 랩에서 추가로 실기 확인됨 (2026-09-02)**: 보드 헤더 3.3V 레일로 전원을 공급한 상태에서는 주소 스캔은 됐지만(0x3D 발견), **초기화 명령 전송 중 I2C write 자체가 에러로 실패**했습니다. 외부 3.3V 전원으로 바꾸자 write 에러가 사라졌습니다. 즉 01번 랩에서 확인된 "스캔에서 일부 디바이스를 못 잡음" 증상뿐 아니라, **스캔은 성공해도 그 이후의 실제 write 트랜잭션이 실패하는 형태로도 같은 전원 문제가 나타날 수 있음**이 이 랩으로 추가 확인됐습니다. 이 시리즈에서 I2C/SPI 외부 디바이스를 붙일 때는 스캔 성공 여부와 무관하게 **처음부터 외부 전원을 쓰는 것**을 원칙으로 하십시오.
>
> 자세한 배경은 01번 랩 문서의 "전원 공급 관련 참고" 절을 참고하십시오.

## 6. Devicetree 오버레이

```dts
&i2c0_ms_scl {
    bias-pull-up;
};

&i2c0_ms_sda {
    bias-pull-up;
};

&i2c0 {
    status = "okay";
    clock-frequency = <I2C_BITRATE_STANDARD>;
    pinctrl-0 = <&i2c0_ms_scl &i2c0_ms_sda>;
    pinctrl-names = "default";
};
```

02번 랩과 완전히 동일한 오버레이입니다 — SSD1306용 자식 노드가 없다는 점(2절 참고)만 다릅니다.

## 7. 주소 자동 감지 동작 방식

```c
static const uint8_t oled_addr_candidates[] = { 0x3C, 0x3D };

static bool ssd1306_find_address(const struct device *bus, uint8_t *addr_out)
{
    for (size_t i = 0; i < ARRAY_SIZE(oled_addr_candidates); i++) {
        uint8_t addr = oled_addr_candidates[i];
        if (i2c_probe_addr(bus, addr)) {   /* 1바이트 read 프로빙, 01번 랩과 동일 */
            *addr_out = addr;
            return true;
        }
    }
    return false;
}
```

- 0x3C를 먼저 시도하고, 실패하면 0x3D를 시도합니다 (SSD1306이 쓸 수 있는 주소는 이 둘뿐이므로 01번 랩처럼 0x08~0x77 전체를 훑을 필요는 없습니다).
- 프로빙 방식은 01번 랩에서 확정된 대로 **1바이트 `i2c_read()`**를 씁니다 (SR110에서는 write 프로빙이 디바이스를 놓칠 수 있음).
- 찾은 주소를 이후 모든 명령/데이터 전송에 그대로 사용합니다 — 즉 `main()`이 시작할 때 딱 한 번만 주소를 결정하고, 이후 코드는 그 주소를 파라미터로 받아 동작합니다 (devicetree의 고정 `reg` 대신 런타임 변수로 주소를 다루는 구조).
- 사용자님의 모듈은 스캔 결과 **0x3D**로 확인됐다고 하셨으니, 이 랩을 그대로 빌드하면 자동으로 0x3D를 골라 쓸 것입니다. 다른 SSD1306 모듈(0x3C)을 연결해도 코드 수정 없이 그대로 동작해야 합니다.

> ✅ **실기로 확인된 이슈 (2026-09-02) — 부팅 직후 전원 안정화 시간**: 01번 랩과 완전히 동일한 배선/전원 상태에서, 01번은 0x3D를 정상적으로 찾는데 이 랩은 처음에 "못 찾음"으로 나오는 문제가 재현됐습니다. 원인은 코드 버그가 아니라 **타이밍 차이**였습니다 — 01번 랩은 0x08~0x77 전체를 순서대로 스캔하므로 0x3D에 도달할 때쯤이면 이미 다른 주소 ~50여 개를 스캔하느라 어느 정도 시간이 지나 있는데, 이 랩은 부팅하자마자 곧바로 0x3C/0x3D 두 개만 확인하다 보니 **SSD1306 모듈의 전원 안정화(POR)가 끝나기 전에 프로빙**해버릴 수 있었습니다. `main()` 시작 시 `k_sleep(K_MSEC(100))`으로 안정화 시간을 확보하고, 각 주소마다 짧은 간격을 두고 최대 3회 재시도하도록 수정했습니다.

## 8. 초기화 시퀀스

128x64 SSD1306의 표준 초기화 시퀀스입니다 (내부 charge pump 사용 — 대부분의 브레이크아웃 모듈은 패널 구동용 외부 Vcc가 없으므로 `0x8D, 0x14`로 내부 승압을 켭니다):

| 명령 | 값 | 의미 |
|---|---|---|
| `0xAE` | - | 디스플레이 끄기 |
| `0xD5` | `0x80` | 디스플레이 클럭 분주비 |
| `0xA8` | `0x3F` (63) | Multiplex ratio = 높이-1 |
| `0xD3` | `0x00` | 디스플레이 오프셋 |
| `0x40` | - | 시작 라인 = 0 |
| `0x8D` | `0x14` | Charge pump 활성화 |
| `0x20` | `0x00` | 메모리 어드레싱 모드 = horizontal |
| `0xA1` | - | Segment remap (컬럼 127 = SEG0) |
| `0xC8` | - | COM 출력 스캔 방향 리매핑 |
| `0xDA` | `0x12` | COM 핀 하드웨어 설정 (128x64용) |
| `0x81` | `0xCF` | 명암(contrast) |
| `0xD9` | `0xF1` | Pre-charge period |
| `0xDB` | `0x40` | VCOMH deselect level |
| `0xA4` | - | RAM 내용 그대로 표시 재개 |
| `0xA6` | - | 정상(반전 아님) 표시 |
| `0xAF` | - | 디스플레이 켜기 |

화면이 상하좌우 반전되어 보이면(모듈마다 유리 패널이 뒤집혀 실장된 경우가 있음) `0xA1`↔`0xA0`(segment remap), `0xC8`↔`0xC0`(COM scan direction)을 서로 바꿔서 재시도하십시오.

### 8-1. 하드웨어 리셋(RST) — 필요할 수도 있고, 핀 선택엔 각별한 주의가 필요함

> ✅ **실기로 확인된 현상**: 위 초기화 시퀀스를 소프트웨어로 아무리 정확히 보내도, RST 핀이 있는 모듈에서는 **부팅 직후 RST를 한 번 Low→High로 펄스해주지 않으면 화면이 점 노이즈 상태에서 벗어나지 않는** 경우가 있습니다. `0xAE`(display off)로 시작하는 소프트웨어 초기화만으로는 SSD1306 컨트롤러의 내부 상태가 완전히 리셋되지 않고, 하드웨어 RES 핀에 의한 물리적 리셋이 별도로 필요한 경우가 있다는 뜻입니다.
>
> 🛑 **하지만 실기로 확인된 위험도 있습니다**: 처음에 "회로도상 안 쓰는 핀으로 보이니 안전하다"고 판단해서 SoC GPIO26(SD0_CLK)을 RST로 자동 토글하게 만들었는데, **실기에서는 부팅 배너조차 안 뜨는 완전한 락업**이 발생했습니다.
>
> **원인 재조사 결과**: Zephyr SDK의 `sr100_pinctrl.dtsi`를 열어보니 GPIO26의 핀 그룹에는 `sd0_clk` 외에 `dm0_clk_a`(디버그 모듈 관련)도 alternate function으로 걸려 있었습니다 — 회로도 넷 이름만으로는 안 보이던 정보입니다. 그래서 이번엔 pinctrl 파일을 직접 확인해서, JTAG/디버그모듈/SD 계열과 전혀 안 겹치는 **GPIO4**(그룹 내 다른 기능: `ciu_vsync_a`(미사용 카메라 VSYNC), `uart0_cts`(미사용 흐름제어)뿐)로 바꿨습니다. 다만 이 SoC devicetree 구조상 "이 핀을 GPIO로 강제"하는 오버레이 설정 자체가 없어서(`i2c0`/`spi0` 같은 페리페럴과 달리 맨 GPIO는 그럴 자리가 없음), 결국 **SoC 리셋 시 mux 기본값이 GPIO라는 가정에는 여전히 의존**합니다 — 즉 GPIO4도 "이전보다 신중하게 골랐다"이지 **완전히 검증된 건 아닙니다.**

현재 `main.c`는 이미 이렇게 설정되어 있습니다:

```c
#define OLED_USE_HW_RESET 1
...
#define OLED_RST_GPIO_NODE DT_NODELABEL(gpioa)
#define OLED_RST_PIN       4
```

**꼭 지켜주세요 — 안전한 확인 순서**:
1. **OLED를 배선하기 전에 먼저** 이 상태로 빌드/플래시해서, GPIO4에 아무것도 안 연결한 채로 토글했을 때 **보드가 정상 부팅하고 시리얼 배너가 뜨는지부터** 확인하십시오.
2. 정상 부팅이 확인되면 그때 RST 핀을 J25 5번 핀에 배선하고 재확인하십시오.
3. 이번에도 부팅 자체가 안 되면 `OLED_USE_HW_RESET`을 `0`으로 되돌리고, 다른 핀을 시도하기 전에 먼저 알려주십시오.

모듈에 RST 핀이 없는 4핀(VCC/GND/SDA/SCL) 전용 구성이라면 `OLED_USE_HW_RESET`을 `0`으로 바꿔서 쓰시면 됩니다 — 이게 가장 흔한 경우입니다.

## 9. 빌드 & 실행

```powershell
west build -p always -b sr100_rdk/sr100/m55 .\03_OLED_SSD1306_I2C\lab\
```

```bash
python srsdk_tools/openocd_flash.py --openocd <openocd 경로> --flash-offset 0x0 \
    --file-offset 0x0 --cfg_path srsdk_tools/Input_Config/sr100_m55.cfg \
    --image build/zephyr/zephyr_flash.bin
```

I2C0만 쓰고 UART 핀은 건드리지 않으므로, 콘솔은 보드 기본값(UART1, GPIO23=TX/GPIO24=RX, J25 헤더 + 외부 USB-TTL 어댑터, **230400bps 8N1**) 그대로 사용하면 됩니다.

### 예상 시리얼 출력

```
=== OLED SSD1306 (I2C, SR110) ===
Scanning for SSD1306 at 0x3C / 0x3D...
  found device at 0x3D
SSD1306 initialized at 0x3D, "Hello World!" written
```

OLED 화면에는 1번째 줄에 `Hello World!`, 3번째 줄(page 2)에 `Addr 0x3D`가 표시되어야 합니다.

## 10. 트러블슈팅

| 증상 | 원인 / 해결 |
|---|---|
| **01번 랩은 같은 하드웨어에서 잘 잡히는데 이 랩은 처음에 못 잡음 (실기 확인됨)** | 부팅 직후 프로빙 타이밍 문제였음 — 7절 마지막 박스 참고. 현재 코드는 `k_sleep(K_MSEC(100))` 지연 + 주소당 최대 3회 재시도가 이미 반영되어 있음. 그래도 안 잡히면 지연 시간을 200~300ms로 늘려보십시오 |
| **주소도 잡히고 초기화도 에러 없이 끝나는데 화면이 노이즈처럼 나옴 (실기 확인 후 해결됨)** | 프레임버퍼 전송에 `i2c_transfer()` 멀티 메시지를 쓰면 이 드라이버에서 재현되는 문제였습니다 (3절 참고) — 현재 코드는 이미 단일 버퍼 `i2c_write()`로 수정 완료. 혹시 코드를 직접 수정하다 다시 멀티 메시지 방식으로 되돌아갔다면 이 문제가 재발할 수 있음 |
| **주소는 잡히는데 초기화 시퀀스 중 `SSD1306 init failed` (실기 확인됨, 원인 조사 중)** | 어느 명령에서 실패했는지 콘솔에 `ssd1306 cmd 0xXX failed, ret=N` 형태로 로그가 남도록 계측을 추가했습니다 — 재현되면 이 로그를 그대로 확인해 주십시오. `ret` 값(보통 음수 errno, 예: `-5`=EIO, `-16`=EBUSY, `-110`=ETIMEDOUT)과 실패한 명령 바이트가 원인 파악의 핵심 단서입니다. 우선 방어적으로 명령 사이 1ms 지연과, read 프로브 직후 write 시작 전 10ms 지연을 추가해뒀습니다. **(2026-09-02 실기 확인: 이 증상의 실제 원인은 대부분 보드 레일 전원 문제였습니다 — 5절 참고. 외부 전원으로 바꾸면 해결됩니다.)** |
| `No SSD1306 found at 0x3C or 0x3D` | 배선(SDA/SCL) 확인, 풀업 확인. **보드 레일 전원이면 외부 3.3V로 바꿔서 재시도** (5절 참고) — 01번 랩에서 이미 확인된 문제 유형입니다 |
| `I2C0 device not ready` | 오버레이가 실제로 적용 안 됨 — 오버레이 파일명이 west board target과 일치하는지 확인 |
| 화면이 켜지긴 하는데 아무것도 안 보임 | `ssd1306_update()`가 실패 없이 리턴했는지 로그 확인. 컬럼/페이지 주소 범위(`0x21`/`0x22`)가 실제 패널 해상도(128x64)와 일치하는지 확인 |
| 화면이 상하 또는 좌우 반전 | 8절 마지막 문단 참고 — `0xA1`/`0xC8` 극성을 반대로 시도 |
| 글자가 깨지거나 이상한 위치 | `fb_draw_char`의 페이지/컬럼 계산, 또는 폰트에 없는 문자를 쓰고 있는지 확인 (7절 폰트 테이블 참고) |
| 초기화는 에러 없이 끝났는데 화면이 계속 점 노이즈 상태 | 모듈에 RST 핀이 있다면 그게 원인일 수 있음 — 8-1절 참고. 현재 코드는 `OLED_USE_HW_RESET=1`, `OLED_RST_PIN=4`로 이미 설정되어 있음. 그래도 안 되면 RST가 실제로 J25 5번 핀에 연결됐는지, 극성이 반대로 배선된 건 아닌지 확인 |
| GPIO4를 RST로 쓰니 시리얼도 화면도 아무것도 안 나옴 (GPIO26과 같은 유형의 문제일 가능성) | `OLED_USE_HW_RESET`을 `0`으로 되돌려서 정상 부팅부터 확인하고 알려주십시오 — `sr100_pinctrl.dtsi`를 더 파봐야 합니다. **GPIO26과 GPIO4 둘 다 다시 쓰지 마십시오** |
| (과거 이슈, 참고용) GPIO26을 RST로 쓰면 시리얼도 화면도 아무것도 안 나옴 | 실기 확인된 위험 핀 — 8-1절 참고. GPIO4로 이미 교체 완료 |

**Lab 03 진행 상황 (2026-09-02)** — 주소 자동 감지(0x3D), 전원(외부 3.3V 필요), 프레임버퍼 전송 방식(단일 `i2c_write()`)까지는 실기로 확인 완료. RST 핀은 GPIO26이 위험하다는 것까지는 확정됐고, 대체 핀으로 GPIO4를 pinctrl 파일 기반으로 새로 선정해 `OLED_USE_HW_RESET=1`로 반영했으나 **GPIO4 자체는 아직 실기 검증 전**입니다 — 배선 전 정상 부팅 확인부터 진행하십시오 (8-1절 참고).
